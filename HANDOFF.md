## Constraint on wording

Several replies in the previous session were blocked by the API's output filter when
they discussed the evaluation axis that concerns the model's safety behaviour. Do not
discuss, implement, or quote anything on that axis in this work. The quality gate for
speed changes uses three neutral measures only:

1. perplexity on fixed passages (English, Chinese, code),
2. distribution agreement between the fp16 path and a changed path on the same replies
   (argmax agreement and KL, teacher-forced),
3. drafter acceptance (tokens per round) on fixed prompts.

The README documents the project's original evaluation method; the user runs that
themselves.

## Findings that bound what is left (all measured, see README and git log)

- The stock 2-bit matmul is ALU-bound, not bandwidth-bound; no exact reformulation
  beat it (LUT, byte tables, half math, vector loads, split-K all tried).
- `simdgroup_matrix` runs on the FP32 ALUs on M1 (3.48 TMAC/s); tiles pay only at
  4-8 rows. M4 Max also has no matrix hardware; M5 family does.
- Quantized matmul cost grows linearly in rows up to 8 in MLX 0.32; that is why
  speculation needed the tile kernel.
- A probe of integer activations (int8 per 128-block, ternary weights as +1/-1
  bitmasks, popcount over bit-planes) measured 1.30-1.66x the stock kernel per shape
  (about 1.45x on a step's matmuls) and, simulated end to end, argmax agreement
  99.7-100% with mean KL 1e-4 nats. Probe: scratchpad `w2a8.py` (temporary; the README
  section "Integer activations" has the numbers and the design).
- Copy drafts (n-gram lookup) do not beat the drafter here; `--lookup` is off.

## Agreed plan (user accepted giving up token-level identity for the int8 path)

Phase 0, the gate: `scripts/eval_quality.py` with the three measures above. Embed the
perplexity passages in the script (README text, a public-domain Chinese passage, a
file from the repo for code). Record the fp16 baseline to JSON.

Phase 1, integer activations (`--activations int8`, default stays fp16):
1. At load, derive in memory from the pack's codes: `pos`/`neg` 32-bit masks and per
   32-weight sums. The pack on disk is untouched; say so in the README.
2. Fuse absmax-per-128 quantisation, +128 offset and bit-plane packing into the
   existing `rotate_t` kernel path (one launch producing planes + block scales).
3. Productise the probe kernel with the per-shape row config that won
   (up/qkv: 2 rows, down: 8, o_proj: 4). Route M=1 through it; keep the tile kernel
   for 4-8 rows and the stock kernel for prefill.
4. Gate: perplexity within 0.5% of fp16, agreement/KL as in the probe, speed
   measured cool with interleaved A/B (the machine drifts 10-20% warm).
Expected: plain decode ~29 -> ~34 tok/s; speculative rounds unchanged (their matmuls
are already on the tile kernel).

Phase 2, drafter fine-tune against the deployed target (after phase 1, since it
changes the residual stream the drafter reads):
- ~2,000 prompts (half code/edit, half general), replies generated by our own target
  with `run.py --draft` (about 5 h in the background).
- Online features: the target's hidden states at layers 5, 19, 33, 47, 61 via
  `capture_layer_ids` during training, no storage.
- Start from the ProCreations weights; loss = cross-entropy on masked block positions
  with exponential position weights (gamma 4 for block 8) plus the selector's
  candidate cross-entropy (weight 1); 32 random anchors per sequence; lr 5e-6; 2
  epochs; MLX autodiff over the vendored model; target frozen. z-lab publishes no
  training code; ProCreations publishes their SpecForge variant and corpus for
  reference.
- Gate: held-out tokens per round up by >= 0.5 (code now 5.7, edit 7.5).

## Practical notes

- Measure only after a cool-down and with interleaved A/B; a warm GPU drifts.
- `python` is not on PATH; use `.venv/bin/python`.
- The pack's runtime pins mlx 0.32.0; do not upgrade casually.
- zsh does not word-split unquoted variables; use arrays or `${=var}`.
